# 阶段 32：采购创建持久防重与精确恢复

基线 `9496b0c`，分支 `codex/stage32`。本轮继续本地模拟，不接真实第三方或公网。

## 实现与兼容

新增需求的 `creationRequestId`、服务端四字段 SHA256 摘要和需求在同一事务提交；唯一约束竞争的失败事务回滚后读取原结果。同标识同内容返回原编号，不覆盖编辑或合并后的数据；不同内容 409。不同标识可以合法创建相同内容。首次创建检查 SKU/仓库，成功请求重放不依赖它们再次在线。

007 增量迁移只扩展 `wms_purchase_detail`：可空 ASCII 二进制请求标识、摘要、默认 0 的删除标记和唯一索引。需求统一逻辑删除，普通 MyBatis 查询/详情/合并/统计不包含删除记录；重复删除成功，原创建结果可查为已删除，旧请求重放 409，不提供复活操作。客户端不能写入删除标记或内部摘要；更新不改变原创建元数据。保存、更新、删除仅 POST，保留 CSRF。

- `POST /api/admin/ware/purchasedetail/save`：新增可选 `creationRequestId`，响应仍为 `R + id`。
- `GET /api/admin/ware/purchasedetail/creation/{requestId}`：`R + found`，存在时附 `id/deleted/status/purchaseId`，不返回摘要。
- 旧无标识接口兼容，但没有持久创建防重保证。阶段 27 的旧标签页快照继续人工候选核对，不补造标识。
- 新快照结果未知后冻结原内容，刷新仍可精确查询或重试；已删除结果只允许核对结束记录，不自动新建。

Test、Test Recovery 和 Demo 两代恢复启动前均接入 007。迁移检查覆盖重复执行、历史字段、重复标识预检、唯一约束和删除后标识仍被占用。

## 复现及验收

先恢复 Docker/模拟环境，18 项诊断健康，再在实际 `_test` 数据库复现旧接口：同一请求标识及内容产生两个不同编号。记录在私有 `.tools/stage32-baseline.json`，不使用 Demo 夹具。

Demo 冷备份 `.data/backups/stage32-before` 包含 SQL、Redis、图片、模拟台账；密钥仍私有独立保管。007 前后原采购字段投影一致，不初始化原库。

已完成的定向检查：相关 Maven 构建及新增 2 项 Java 测试、前端 lint/build、Node 48 项；Admin 11 个业务场景（含新增持久防重场景；原始 12 节点含父节点），Chromium/Edge 采购各 4 项，共 8 项。浏览器实际丢弃真实保存响应后刷新，按原请求查询同一编号；旧快照人工核对继续通过。并发、内容冲突、元数据写入保护、编辑/合并/删除重放及仓储重启均验证。

最终 POST 方法限制与同请求重放检查、原数据核对及健康结果在私有阶段摘要归档。完整 All、全量 Browser、自然 Session TTL 和两类 Recovery 留在阶段 35 集中执行，不把专项结果计作全量通过。

本轮不修改订单状态机或期限，沿用阶段 13 自然 30 分钟证据。不承诺不同请求标识的内容自动去重；跨标签只有同标识重放受保护。
