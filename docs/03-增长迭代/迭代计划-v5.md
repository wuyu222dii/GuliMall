## 三、下一轮建议：阶段 27–31

核心目标只有两个：采购操作的上下文与结果明确；现有后台资料可以可靠查找、往返和继续编辑。继续开发验证码、本地图片和持久模拟支付，不新增真实服务。

| 阶段 | 核心交付 | 预计投入 | 前置 |
|---|---|---:|---|
| 27 | 采购操作结果与选择器闭环 | 14–22 小时 | 当前基线及健康模拟环境 |
| 28 | 后台商品筛选和订单导航 | 10–16 小时 | 27 |
| 29 | 基础资料查询与列表分页 | 8–12 小时 | 28 |
| 30 | 未保存输入保护及消费者入口收口 | 8–14 小时 | 29 |
| 31 | 定向测试、完整回归和交付归档 | 12–20 小时 | 30 |

合计 52–84 小时，含约 20% 缓冲为 63–101 小时。按过去每周 8 小时的换算假设约 8–13 周；这不是交付承诺，也不是前轮实测耗时。阶段 27 完成后校准。每阶段拆成 2–4 小时任务，验收后独立提交，不自动推送或合并。

### 阶段 27：采购操作结果与选择器

1. 在独立 Test 先复现：A 明细已打开，切换 B 后请求延迟/失败；新增需求提交成功但响应丢失；领取/完成响应未知；重复点击。验证是否存在旧明细可继续提交的情况。
2. 明细查询开始清除或明确标为旧数据，加载/失败时禁止领取、完成；响应必须绑定当前采购编号。换单不得把另一单 results 套入当前操作。
3. 写入增加即时提交锁，区分保存确认、刷新失败和结果未知。新增返回 id 后绑定原需求；响应丢失时保留快照、暂停自动重发，允许查找候选后人工核对。不能凭相同 SKU/数量就自动认定唯一成功，也不宣称新增接口已有服务端持久幂等。
4. 已合并、领取、完成的原请求优先查询真实结果；同一需求若已归属采购单，核对归属后跳转；冲突明确提示。继续使用原本的入库事务和幂等逻辑。
5. SKU 选择器按名称/编号分页，保留已选编号；合并目标复用已有 unreceive/list，独立分页、按编号/仓库查询，不受当前采购列表页限制。补需求 SKU/采购单号查找入口。
6. 按当前页签加载所需数据，避免库存查询失败把采购明细页一起清空；查询失败显示可恢复错误，不给出“暂无数据”的业务结论。

验收：超过 50 个同关键词 SKU、跨页采购单均可选择；延迟/失败不会操作旧单；新增未知结果不自动再创建；重复完成只入库一次；Chromium 完整操作、Edge 和 375px 关键操作通过，原库存不被夹具修改。

### 阶段 28：后台商品筛选与订单导航

1. 商品列表接通已有 status、brandId、catalogId；关键词、筛选及页码写入 URL，提供清除，编辑后返回保持条件。分类/品牌显示名称并保留编号。
2. 后台订单筛选/页码写入 URL，增加清除入口和 /admin/orders/:id 独立详情；复用现有详情、处理进度和发货组件。刷新、复制和返回均可恢复上下文。
3. 未登录 401、非管理员 403，后端仍校验分页、编号和枚举。参数非法明确失败，不依赖前端隐藏按钮。
4. 同步页补现有下次重试时间及商品编辑链接，仍显式区分“任务已提交”和“已同步”。不新增批量强制改状态按钮。

验收：商品组合筛选、多页返回、订单直接详情及重登回跳正确；未支付/库存未确认订单仍不能发货；失败不把旧数据当新结果。Chromium/Edge 覆盖查询和导航。

### 阶段 29：基础资料可查找

1. 品牌、属性分组、属性增加名称/编号检索，分组/属性增加分类和现有状态条件；分类保留树关系，提供名称/编号定位。
2. 先复用当前 metadata 在页面筛选与分页，稳定排序，空页回退；不因筛选把其他记录从业务数据中删除，不对切片数据执行全量覆盖。
3. 保存/删除后定位当前记录或合理页码，明确成功和刷新失败；已有引用删除保护及停用规则继续由服务端执行。
4. 本阶段不拆成通用表格框架，不引入数据表库；全量 metadata 的后端分域/分页留作数据量增长后的单独优化。

验收：多页同名/相近名称及不同分类数据可准确定位；编辑、删除引用拒绝、保存后查询正确；后台筛选不改变消费者分类树与商品既有属性。

### 阶段 30：输入保护及消费者入口

1. 地址、基础资料、仓库、采购需求和发货表单的未保存修改，覆盖站内离开、切换编辑对象、取消编辑；关闭/刷新保留浏览器提醒。只提醒有修改的表单，保存成功后清除脏标记。
2. 结果未知的提交沿用原有锁定/快照规则，不用“放弃编辑”自动重发；提醒功能不清除商品创建请求或结算提交令牌。
3. 不把地址、密码、验证码自动保存到浏览器持久存储；本轮不做自动草稿框架。
4. 首页补“查看全部分类/展开”，第 11 个及以后的一级分类有明确入口；顶部文案与实际行为一致。保留搜索页的全分类选择。
5. 商品详情“立即购买”改为与当前加购后到购物车的行为一致的名称/提示，不新建绕过购物车的订单流程。

验收：保留编辑/确认离开均可用，保存后不误拦；未知提交仍可恢复；全分类、键盘操作和 1280px/375px 通过，表格仅在自身容器滚动。

### 阶段 31：回归与交付

1. 新增采购明细竞态、结果未知、选择器分页、后台组合筛选/导航和脏表单测试。只拦截延迟、断开或丢失响应，不用假成功数据替代真实业务。
2. 保留当前 72 个业务场景，新增场景另计；执行适用 Java/Node/PowerShell、前端 lint/build、Diagnostics、Chromium 连续两轮完整链和 Edge 关键场景。旧 9 类/17 方法忽略不增加、不计通过。
3. Test Recovery 复验；若涉及持久化写入语义、迁移、支付台账或恢复脚本，重跑 Demo 完整隔离恢复。纯页面/只读筛选不改这些边界时，可沿用阶段 26 Demo 证据，明确本轮未重跑，不混作新通过。
4. 若改订单状态机或期限，重新做自然 30 分钟；否则沿用阶段 13。自然 Session TTL 若补验，独立记录，不能以“另标签退出”替代自然过期。
5. 成功和失败均恢复调用前模式；归档版本、日志、脱敏截图、失败修复及哈希，更新 README/接口/演示检查表。最终常驻 18 项健康，原演示订单、库存、图片、密钥与台账保留。

## 四、统一边界与执行顺序

- 先阶段 27 的采购结果安全，再查找效率，最后补表单与消费者入口。不要把已完成的地址默认、商品创建防重、购物车、会员订单筛选再做一遍。
- 继续 Java 8、Boot 2.1.8、React、单管理员、同源 /api、R/PageUtils、Session/CSRF 和服务端归属/金额校验。
- 本建议不需要新增业务表或字段。若另行要求采购新增的跨重启持久幂等，再单独设计已有表增量迁移；不以界面禁用冒充服务端保证。
- 不初始化或覆盖 Demo 库，不清理人工交易；夹具只在经过实际库名校验的独立 Test 中建立。数据库升级必须另做冷备份及迁移验证。
- 本次计划核对仅产出文档，不实施上述功能。后续用户已单独授权整合现有分支并推送 main，本计划随独立文档提交发布；阶段 27–31 仍待实施。

## 五、仍缺失但建议后置的功能

会员资料中心、修改/找回密码、退款退货售后、优惠券/积分结算、秒杀、角色权限、多管理员、运营报表、首页运营后台、真实物流轨迹、盘点调拨与手工库存业务，均未形成完整页面与业务闭环。它们需要另立范围，不把现有实体/CRUD 当作已完成，也不混入这轮页面收口。

真实支付宝/公网通知、真实短信和 OSS 继续不接。独立机器、第二位操作者、实体手机、Firefox/Safari、自然 Session TTL、容量、高可用和在线热备继续待补验或后置。本地模拟通过不代表这些能力已验证。
