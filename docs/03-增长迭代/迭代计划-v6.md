### 阶段 32：采购需求创建持久防重

1. 先在独立 Test 复现提交成功但响应丢失、刷新恢复、相同标识并发、服务重启后重试；保留阶段 27 的旧请求兼容及人工核对入口。
2. 新增需求首次提交固定 creationRequestId 和原快照；服务端按固定业务字段计算摘要。在现有采购需求表增加可空请求标识/摘要及唯一约束，与需求同一事务保存，不新增业务表、不建立通用框架。
3. 同标识同原内容返回原编号；同标识不同内容 409。校验/事务失败不留下部分记录。需求后续被修改或合并后，原创建重试不覆盖当前记录。
4. 管理员只读查询原请求结果；响应未知时继续锁定原快照，查询/重试仍用原标识。旧版未携带标识调用继续兼容，但不宣称具有同等保证。
5. **删除语义必须同时设计：**不能物理删掉请求标识后让旧请求重新创建。建议对携带标识的删除记录保留最小逻辑删除标记及原标识；普通列表/统计/合并排除已删除记录，原请求查询报告已删除，重试拒绝复活。旧记录兼容，不清理历史数据。
6. 两个独立新标识可以合法创建同内容需求；不按相同 SKU/数量自动去重。跨标签只有重放同一标识时受保护，不能宣传所有跨标签新建都自动合并。
7. 空库脚本与增量迁移同步维护；先查重，Test 验证后冷备份 Demo 再迁移；既有订单、库存及采购引用不变。

验收：并发同请求只一条；已提交丢响应和重启后可准确查回；改内容 409；编辑/合并/删除后原创建重试不覆盖、不复活、不重复入库；旧接口及权限仍正确；浏览器可继续下一条需求。

### 阶段 33：补齐输入保护遗漏

1. 先复现采购完成结果：修改某项为失败并输入原因，依次切单、切页签、筛选、翻页、刷新列表、站内离开、退出及刷新浏览器，核对是否无提示丢失。
2. 将尚未提交的完成结果绑定原采购编号和基线，进入现有脏表单保护；选择继续编辑保留全部结果，明确放弃后才清除。只读刷新不擅自覆盖输入，空白/未改表单不误拦。
3. 已发送但结果未知的完成请求继续使用阶段 27 原快照，不能被“放弃编辑”更换编号、清空或重发；重复完成仍由服务端幂等保护。
4. 商品编辑优先复用已有共享 guard，覆盖退出前确认；取消退出不发 logout，确认退出最多一次。保留商品创建 requestId、快照、校验失败修正和查询恢复语义。
5. 保存/上传期间阻止引发结果不明的离开，或明确保留可查询原结果；不新增自动草稿，不把密码/地址等敏感输入写进持久存储。

验收：Chromium/Edge 覆盖上述实际复现链、保存/上传延迟和响应丢失；375px/键盘确认可用；已完成发货表单等原保护不回退，商品和订单原标识逐字保留。

### 阶段 34：后台查询恢复与同步定位

1. 采购页签、需求/采购单/库存筛选、列表页码和当前采购单编号进入 URL。基础资料类型/查询/页码、仓库查询/页码也可恢复；编辑草稿、勾选集合和待确认写入快照不放 URL。
2. URL 与当前标签页待确认原请求冲突时，优先显示原操作核对，不允许 URL 自动触发写入或覆盖原请求；有脏输入时按阶段 33 确认后再切查询上下文。
3. 同步列表新增精确 SPU 编号和同步状态筛选、清除、URL 页码；后端查询和总数使用同一条件。商品列表/编辑可跳转此 SPU 同步记录，返回不丢商品条件。
4. 复用现有 R/PageUtils、参数校验、权限和安全重试。保持“已提交任务”与“已同步”区分；不新增直接改状态按钮，也不引入监控平台或通用数据表框架。
